[공통 명세] Rust Top-down 소스 배치 원칙
=======================================

1. 'Top-down'의 정확한 의미
- 최상단에서는 모듈이 외부에 제공하는 API와 핵심 흐름이 드러나야 한다.
- 호출자는 '무엇을 하는지' 읽고, 아래의 로컬 함수/하위 모듈에서 '어떻게 하는지' 읽는다.
- Rust의 이름 해석은 선언 순서와 무관하므로 함수를 먼저 배치할 수 있다.
- 단, `use`, `mod`, 상수, 타입, `impl`의 자연스러운 묶음을 무너뜨리지 않는다.

2. 파일별 권장 순서 (엄격한 강제 템플릿 아님)
  A. 모듈 설명 (`//!`) / import / mod 선언
  B. 공개 API, 대표 엔트리포인트 및 외부에 노출되는 타입
  C. 대표 엔트리포인트와 직접 관련된 조립/오케스트레이션
  D. 세부 구현, 변환, 검증, 내부 상태/헬퍼
  E. `#[cfg(test)] mod tests;` (해당되는 경우)
- `struct`가 핵심 공개 타입이라면 `struct` 선언 + 해당 `impl`의 공개 메서드를 함께 배치한다.
- Helper를 숨기려고 의미 없는 forwarding 메서드를 만들지 않는다.
- trait 구현은 해당 타입의 역할이 드러나는 위치에 붙여 두며, 제네릭/라이프타임을 훼손하지 않는다.
- const, type alias, macro, attribute 등은 해당 API의 이해에 필요한 위치에 둔다.

3. 함수 및 메서드 순서
- `main`, `run`, `serve`, `optimize`, `solve` 등 상위 호출 흐름을 앞에 둔다.
- `impl` 내부에서는 public 생성자/메인 동작 → 조회/보조 public 메서드 → private 메서드 순을 우선 검토.
- private helper는 상위 로직 아래에서 호출 흐름/책임 순으로 배치한다.
- 독립 함수가 더 단순한 경우 `struct + impl`로 강제로 이동시키지 않는다.
- `async/await`, `?`, 명확한 `let` 바인딩 중심으로 읽히게 한다.
- `.and_then().map_err()` 연쇄나 Rx-like 플로우를 목적으로 새 추상화를 도입하지 않는다.

4. 모듈과 공개 API 규칙
- `pub`, `pub(crate)`, `pub(super)`, `pub(in ...)`, `pub use`, 모듈 경로를 보존한다.
- 공개 함수/타입의 시그니처, 제네릭 bound, trait impl, 에러 타입, 사용 계약을 변경하지 않는다.
- `lib.rs`, `solver/orchestrator.rs`, `routing.rs`처럼 이미 facade 역할인 파일은
  mod 선언 + re-export만으로 충분히 Top-down일 수 있다. 정의 복제 금지.
- `pub use xxx::*`를 변경하거나 import 정리하는 별도 리팩토링은 이 작업 범위에서 제외한다.
- 파일 간 이동은 진짜 책임 경계가 명확할 때에만; 기본값은 같은 파일 내 재정렬.

5. 의미 보존
- JSON / HTTP 응답, serde attribute, 상태 코드, 오류 문자열, 검증 순서 보존.
- Job 제출/완료/복구, 요청 기록 시점, Cancellation/Timeout/동시성 설정 보존.
- Solver 선택, 랜덤 시드, 평가 순서, tie-break, 포트폴리오 실행 보존.
- `#[cfg(...)]`, `#[instrument]`, `#[derive(...)]`, doc comment를 해당 항목과 함께 이동.
- `unsafe`, macro, trait impl 관련 코드의 재배열이 위험하면 변경하지 않고 보고.

6. 테스트/탐색성
- 이미 별도 tests.rs로 분리된 테스트는 유지. 필요한 경우 module declaration만 하단 배치.
- `src/**/tests.rs`는 단위 테스트이며 기존 private 접근을 그대로 유지한다.
- `tests/`는 공개 API 수준 통합 테스트이며 임의 이동 금지.
- 모든 파일을 억지로 비슷한 길이로 맞추지 않는다. 파일 길이는 성공 지표 아님.

완료 판정
- 각 대상 파일을 위에서 아래로 읽었을 때 대표 진입점과 단계가 먼저 드러난다.
- 정리로 인한 코드 복제/새 공개 API/새 의존성이 없다.
- 테스트 동작과 공개 인터페이스가 변경되지 않는다.
