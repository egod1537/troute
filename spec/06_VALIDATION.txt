[검증] 구조 리팩토링 안전성 / 완료 조건
=====================================

작업 전
- `git status --short`로 워킹 트리 변경 사항 확인. 사용자 변경사항 덮어쓰지 않는다.
- `impl` 브랜치 HEAD 확인. 기준 ea1f201ae5af79e71e13589188a7a4bb5a161727
  이후 변경이 있으면 실제 코드에 맞춰 명세를 적용한다.
- 가능하면 `cargo test --all-targets --all-features -- --list` 결과를 별도로 저장하여
  리팩토링 후 테스트 목록 비교에 사용한다(환경 의존으로 실패하면 기록).

각 단계 진행 중
- 이동 전후 함수/메서드의 시그니처, visibility, generics, trait bound, attribute 비교.
- test module의 `#[cfg(test)]` 및 외부 모듈 접근 권한 유지.
- rustfmt가 생성한 변경도 `git diff`로 검토하고 무관한 포맷 변경 최소화.
- 기존 함수 본문의 실행 로직 및 분기 순서 변동이 있는지 diff 리뷰.
- 함수/파일 이동으로 public module path가 변하지 않았는지 확인.

검증 명령
```
cargo fmt --all -- --check
cargo clippy --all-targets --all-features -- -D warnings
cargo test --all-targets --all-features
git diff --check
```
- 사용 가능한 프로젝트 표준 테스트/벤치마크 스모크 테스트가 있으면 해당 명령도 실행.
- all-features가 외부 SCIP 등 환경 의존으로 실패할 경우 원인을 보고하고,
  가능한 기본 feature 빌드/테스트를 추가 실행. 실패를 '성공'으로 표현하지 않는다.
- 기본형 추가 검사 (필요 시): `cargo check --all-targets`, `cargo test`.

회귀 확인
- HTTP endpoint/method, JSON/error/status, body limit, logging/observation
- Cancellation, Timeout, job recovery, persisted error 우선순위
- Solver 결과, deterministic seed, resource budget, telemetry
- Integration Test: tests/http_api.rs, tests/server_startup.rs 등 현존 파일
- 테스트 파일 개수보다 '테스트 항목' 및 assertion 변화 여부를 우선 비교한다.

최종 보고 형식
1. 수정된 파일 / 단계별 요약
2. 대표 entrypoint 위치와 하위 구현의 배치 변화 예시 2~4개
3. 변경하지 않은 파일과 이유(이미 Top-down 등)
4. 공개 API/동작/의존성/테스트 변동 여부
5. 검사 명령별 성공/실패, 환경 의존 blocker
6. 추가 기능 리팩토링이 필요한 곳은 이번 변경과 분리하여 제안

완료 조건
- public API / route / serde / error / algorithm behavior unchanged.
- 프로덕션 및 테스트 코드의 빌드가 확인되거나 실패 원인이 명시됨.
- 단순 정렬 목적에 비해 과도한 설계 변경/새 추상화가 없음.
